## Product design

### Goals / Non-goals

**Goals**: ship a first-version `kpn-mcp` server exposing three agent-callable tools backed by KPN's public APIs:

1. Look up current network disturbances for a Dutch address.
2. Look up maximum internet speed and available carrier technology (fibre/copper) for a Dutch address.
3. Look up the most recent SIM-swap date for a mobile number (fraud/account-takeover signal).

**Non-goals** (explicitly out of scope for this version):

- KPN GRIP and Vonage Number Insights (listed alongside Account Takeover Protection under Security > Identity on the portal, but not named by this ticket or the prior pass — adding them is a separate ticket).
- KPN High Level Design Fttx (fibre network design product, distinct from the consumer speed-check API; not named by this ticket).
- Any write/provisioning capability against a KPN account — all three capabilities are read-only lookups.
- A risk score or fraud verdict derived from the SIM-swap timestamp — the tool returns the raw fact (last swap date); scoring/thresholding is a platform or caller concern, not this connector's.
- OAuth token management UI or credential storage — per the MCP contract, credentials come from request Headers on every call (see Tech design §7).

### Acceptance criteria AC1..AC6

- **AC1**: Given a valid Dutch postal code and house number, When an agent calls the disturbance-check tool with valid KPN credentials, Then it returns a structured result listing any current broadband/fixed/mobile/generic disturbances for that address, or an explicit empty result when there are none (an empty result is not an error).
- **AC2**: Given a valid Dutch address (postal code, house number, optional house-number extension), When an agent calls the internet-speed-check tool with valid KPN credentials, Then it returns the maximum download/upload speed and which carrier technologies (fibre/copper/none) are available at that address.
- **AC3**: Given a valid mobile number, When an agent calls the SIM-swap-check tool with valid KPN credentials, Then it returns the timestamp of the most recent SIM change for that number, or a documented "number not recognized" result if KPN does not know the number.
- **AC4**: Given any of the three tools is called without the required KPN credential Headers, When the request reaches the service, Then the service returns HTTP 401 listing the missing Header name(s), and no call is made to KPN's API.
- **AC5**: Given two concurrent requests from different tenants carrying different KPN credentials, When both call a tool at the same time, Then each request is served using only its own credentials — neither the OAuth token nor any response data from one tenant's call is observable in the other's.
- **AC6**: Given KPN's API returns an error (invalid argument, unauthorized, unknown number, a concurrent-request conflict, rate limiting, or a 5xx/timeout), When the tool call fails, Then the tool returns the structured error envelope (`{"error": {"code", "message", "retryable"}}`) with a code from the fixed vocabulary — never a raw exception, and never a bare HTTP 500 from this service.

## Tech design

### Conclusion

Build a new Python 3.12 + FastMCP service (main line A, vendor-mcp-development SOP) exposing three read-only tools (`kpn_check_disturbance`, `kpn_check_internet_speed`, `kpn_check_sim_swap`), each a thin wrapper over one KPN REST endpoint. Credentials (KPN OAuth2 client ID/secret) come from two request Headers per the SOP's contract; the service exchanges them for an access token per request (with a short-lived, credential-keyed in-memory cache — see §7) and never falls back to environment variables. No gateway change needed.

### Option analysis

| Option | Approach | Pros | Cost | Verdict |
|---|---|---|---|---|
| One MCP server, 3 tools, one FastMCP app (chosen) | Single repo, single container, one tool per KPN capability | Matches "tool = capability" guidance (SOP §2.1); simplest to operate and publish; KPN's 3 products share one auth model | Tools span 2 different KPN product families (network vs. identity) sharing one token — acceptable, same vendor, same credential pair | Chosen — no reason to split |

### Data & API contract

**Credentials (request Headers, per SOP §3.1)**:

| Header | Required | Meaning | Where to obtain |
|---|---|---|---|
| `X-Kpn-Client-Id` | Yes | OAuth2 client ID | KPN Developer Portal → app registration |
| `X-Kpn-Client-Secret` | Yes | OAuth2 client secret | KPN Developer Portal → app registration |

Missing either → `401` with body `{"error": "missing_headers", "missing": ["X-Kpn-Client-Id", ...]}` (SOP §3.2); no call is made to KPN.

**Tool 1 — `kpn_check_disturbance`** (readOnlyHint, idempotentHint)

- Args: `zip_code: str` (Dutch postal code, e.g. `"1234AB"`), `house_number: int`.
- Calls `GET https://api-prd.kpn.com/network/kpn/disturbance-check/address?zip_code=<zip_code>&house_number=<house_number>`.
- Returns (trimmed per §2.5 field-trimming — drops the SMS/email communication-count fields, which an agent has no use for):
  ```json
  {"has_disturbance": true, "disturbances": [
    {"id": "...", "service": "I-TV", "state": "open", "description": "...", "start_date": "...", "end_date": null, "region": null}
  ]}
  ```
  Empty KPN response (all four arrays empty) → `{"has_disturbance": false, "disturbances": []}` — a normal result, not an error (AC1, SOP §4.2's rule that an empty query result is not an error).

**Tool 2 — `kpn_check_internet_speed`** (readOnlyHint, idempotentHint)

- Args: `zip_code: str`, `house_number: int`, `house_number_extension: str = ""`.
- Calls `POST https://api-prd.kpn.com/network/kpn/internet-speed-check/offer` with `{"service_address": {"house_number", "zip_code", "house_number_extension"}}`.
- Returns:
  ```json
  {"max_download_mbps": 500, "max_upload_mbps": 500, "technologies": [{"name": "FIBER", "download": 500, "upload": 500}]}
  ```
  (`technologies` filters out `"NoAccess"` entries into an implicit "not available" — an address with only `NoAccess` returns `"technologies": []`, which is a normal result, not an error.)

**Tool 3 — `kpn_check_sim_swap`** (readOnlyHint, idempotentHint)

- Args: `phone_number: str` (E.164, e.g. `"+31612345678"`).
- Calls `POST https://api-prd.kpn.com/kpn/sim-swap` with `{"phoneNumber": phone_number}`.
- Returns `{"latest_sim_change": "2026-10-29T17:38:22.306Z"}` on success.
- KPN `404 SIM_SWAP.UNKNOWN_PHONE_NUMBER` → tool returns the structured error envelope with `code: "not_found"`, `retryable: false` (not an exception — AC3's "documented not-recognized result").

**Error envelope** (all three tools, SOP §4.2, exact vocabulary — no custom codes):

| KPN status / code | Envelope `code` | `retryable` |
|---|---|---|
| `400 INVALID_ARGUMENT` | `invalid_argument` | `false` |
| `401 UNAUTHENTICATED` | `unauthorized` | `false` |
| `403 PERMISSION_DENIED` | `unauthorized` | `false` |
| `404 SIM_SWAP.UNKNOWN_PHONE_NUMBER` (and any other documented "not found") | `not_found` | `false` |
| `409 CONFLICT` (concurrent request, same MSISDN) | `upstream_error` | `true` (SIM-swap's own doc: a concurrent request for the same number — retrying after the in-flight one finishes is the correct client behavior; there is no better-fitting code in the fixed vocabulary) |
| `429` (assumed, not documented on the pages reached — see Open questions) | `rate_limited` | `true` |
| `500 INTERNAL` / `503 UNAVAILABLE` / `504 TIMEOUT`, connection errors, timeouts | `upstream_error` | `true` |

**DB**: none — this service is stateless and has no database (SOP §1.3).

**Events/messages**: none.

**Backward compatibility**: first version, nothing to be compatible with yet. Per `mcp-track.md` §1.2, this ticket touches only one repo with no cross-repo field/Header dependency, so "release order: no dependency" applies trivially (see Track line).

### Key flow / sequence

```
Agent -> Gateway: tools/call kpn_check_disturbance(zip_code, house_number)
Gateway -> kpn-mcp: POST /mcp  (Headers: X-Kpn-Client-Id, X-Kpn-Client-Secret)
kpn-mcp middleware: read Headers -> ContextVar; missing any -> 401 (short-circuit, no KPN call)
kpn-mcp auth.py: cache lookup by sha256(client_id:client_secret); miss/expired -> POST KPN OAuth token endpoint -> cache with TTL = expires_in
kpn-mcp api_client.py: GET KPN disturbance-check endpoint with Bearer token
kpn-mcp tools/network.py: map KPN response/error -> tool result or error envelope
kpn-mcp -> Gateway -> Agent: structured JSON string result
```

### Non-functional

- **Idempotency & concurrency**: all three tools are pure reads (`readOnlyHint=True`, `idempotentHint=True`); safe to retry. Concurrency safety is the request-level isolation described in §"Multi-tenant isolation" below — no tool has a write path to race on.
- **Performance**: KPN address/number lookups are single-record, no pagination needed; responses are small (well under the 20,000-character ceiling) even before trimming. Outbound timeouts: 5s connect / 30s read (SOP §5); one HTTP client instance reused across calls within a request (connection pooling); total tool-call time including retries kept under 120s.
- **Security**: credentials never leave Headers → `ContextVar` → the one outbound call that needs them; never logged, never written to disk, never placed in a module-level variable (SOP §3.3/§3.4, §6). The only exception discussed and accepted below is the OAuth-token cache, which is explicitly permitted by SOP §3.4 when keyed by a credential fingerprint with an expiry — see next bullet.
- **Multi-tenant isolation** (AC5): credential Headers are read into a `ContextVar` per request and reset in a `finally` block; no global or module-level variable ever holds a credential or a token tied to "the current request" outside that scope. **Decision** (see "Decisions made by DEV01" below): the OAuth access token is cached in-process, keyed by `sha256(client_id + ":" + client_secret)`, with the cache entry's TTL set from KPN's `expires_in` response field (minus a safety margin) — this is the exact exception SOP §3.4 allows ("unless the cache key includes a credential fingerprint and an expiry"). Two tenants with different credentials get different cache entries and never share a token; a request is never served using another request's `ContextVar` value, cached or not.
- **Observability**: structured logs (tool name, truncated/redacted arg summary, KPN endpoint path, KPN status code, latency, error `code`) with a per-request correlation id; credentials, tokens, and raw KPN response bodies are never logged (SOP §6).

### Decisions made by DEV01

(2026-10-30 rule, `mcp-track.md` §2.4 — first-version take-it-or-leave-it choices made without anyone to ask, posted as a separate `[DESIGN DECISIONS]` comment after the `[DESIGN]` stub)

1. **Two Headers, not one combined Header, for the OAuth client credentials** (`X-Kpn-Client-Id` + `X-Kpn-Client-Secret`) — SOP §3.1 requires one credential field per Header; the alternative (packing both into one Header as e.g. `id:secret`) is explicitly disallowed by the SOP, so this is a direct application of the rule, not really an open choice.
2. **Cache the OAuth access token in-process, keyed by a credential fingerprint, instead of fetching a fresh token on every tool call** — trades a small amount of state (explicitly allowed by SOP §3.4 when fingerprint-keyed and TTL-bound) for avoiding an extra network round-trip to KPN's OAuth endpoint on every single tool call. Alternative considered: no caching at all (simplest, fully stateless) — rejected because it roughly doubles KPN API latency and load per call for no isolation benefit, since the fingerprint-keyed cache already gives the same per-tenant isolation guarantee as no caching would.
3. **Unify `house_number` as separate `zip_code` / `house_number` / `house_number_extension` fields across both the disturbance-check and speed-check tools**, even though KPN's own disturbance-check endpoint does not accept an extension field. Alternative: expose the two tools' parameters exactly as each underlying KPN endpoint defines them (disturbance-check without an extension field). Chosen the unified shape because it is one fewer inconsistency for the agent to reason about when both tools are called for the same address in one flow; the extension parameter is simply unused (and not sent) when calling the disturbance-check endpoint.
4. **Treat KPN's `409 CONFLICT` (concurrent request for the same MSISDN) as `upstream_error`/`retryable=true`** rather than inventing a new envelope code — the fixed vocabulary (SOP §4.2) has no "conflict" code, and `upstream_error` is the closest semantic fit (transient, safe to retry after a short delay).
5. **Apply SIM-swap's documented error-code table to the two Network products as well**, since their documentation pages (as reached by this design) did not publish an equivalent table — see Open Questions; this is reversible without any tool-contract change if KPN's actual behavior turns out to differ.

### Decisions made by DEV01 during implementation (beyond the ones already in Tech design)

- Tool descriptions are passed via `@mcp.tool(description=...)` rather than left as the
  Python function's docstring. FastMCP ships `fn.__doc__` verbatim with no dedent, so an
  indented multi-line docstring would leak its leading whitespace into what the Agent sees
  as the tool description — directly against SOP §2.2's "keep descriptions compact". This
  is purely a code-structure choice; the actual description text is unchanged from what the
  Tech design's tool contracts imply and stays within the 500/100-character limits (verified
  by a test assertion, `test_tools_list_snapshot`).
- `httpx.Timeout` requires either a single default or all four of
  connect/read/write/pool set explicitly (the two-keyword form the Tech design assumed,
  `Timeout(connect=5, read=30)`, raises at runtime). Used `Timeout(30, connect=5)` instead,
  which sets write/pool to the same 30s default as read — the Tech design only specified
  connect/read, so this fills the gap with the same value rather than inventing a third
  number.
